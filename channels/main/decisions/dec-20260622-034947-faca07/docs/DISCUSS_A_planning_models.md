# DISCUSS A — Сравнение моделей планирования

_DA11: DISCUSS_* должны явно сравнить и обосновать выбор архитектуры планировщика_

---

## Три кандидата

### A. LLM-only декомпозиция (flat steps)

Оператор передаёт задачу → LLM за один вызов генерирует плоский список шагов → ЛАПА исполняет.

**Плюсы:**
- Просто реализовать
- LLM хорошо знает UI-паттерны
- Нет нужды в явном TaskGraph

**Минусы:**
- Нет реактивности: если шаг 3 провалился, план не обновляется
- Нет per-node контрактов → нет machine-readable done-criteria → нет автоматической проверки завершённости
- Нет retry-бюджетов на уровне шага → бесконечные попытки или потеря контекста
- Нет структурированного восстановления: при отказе всё начинается заново или эскалируется
- Vision-диагностику провала некуда вставить — нет «точки переплана»
- Вся логика проверки остаётся на LLM без детерминированных гарантий

**Вердикт: отклонён.** Не поддерживает реактивное восстановление и per-node проверки.

---

### B. Rule-based task graph (жёсткие рецепты)

Набор заранее написанных «рецептов» (workflow templates) для конкретных задач.
Оператор выбирает шаблон, ЛАПА исполняет детерминированно.

**Плюсы:**
- Максимальная предсказуемость
- Нет риска LLM-галлюцинаций
- Легко аудировать

**Минусы:**
- Не масштабируется: каждую задачу надо написать вручную (противоречит цели «оператор передаёт high-level задачу»)
- Не адаптируется к неожиданным состояниям UI
- Vision-диагностика бесполезна: нет «кто принимает решение о дальнейшем пути»
- По сути это то, что ЛАПА уже делает (навыки = рецепты) — просто с большим набором рецептов

**Вердикт: отклонён.** Не решает задачу автономной декомпозиции.

---

### C. Гибридный планировщик (РЕКОМЕНДАЦИЯ — принято в DA01)

**LLM отвечает за «что делать» (декомпозиция, адаптация, смысл).**
**Детерминированные гейты отвечают за «можно ли делать» (валидация, риск, идентити).**

Архитектура:
1. LLM генерирует иерархический `TaskGraph` (типизированный JSON DAG с per-node контрактами)
2. Детерминированный валидатор проверяет каждый узел: schema, allowed-skill, risk-класс
3. ЛАПА исполняет через 5-гейтовый loop
4. Vision проверяет postcondition → если провал → реактивный перепланировщик (снова LLM)
5. Реактивно созданные узлы проходят ту же валидацию перед исполнением

**Почему именно гибрид:**

| Свойство | LLM-only | Rule-based | Гибрид |
|----------|----------|------------|--------|
| Декомпозиция high-level задач | ✓ | ✗ | ✓ |
| Реактивная адаптация | ✗ | ✗ | ✓ |
| Детерминированные safety-гарантии | ✗ | ✓ | ✓ |
| Machine-readable done-criteria | ✗ | ✓ | ✓ |
| Vision как planning signal | ✗ | ✗ | ✓ |
| Аудируемость | Низкая | Высокая | Средняя-высокая |
| Масштабируемость | Высокая | Низкая | Высокая |

**Ключевое свойство гибрида:** LLM творит в пределах жёсткого закрытого словаря.
Детерминированный гейт отвергает любой узел, нарушающий инвариант.
Это «bounded autonomy» — агентность без unbounded capability surface.

## Граница между LLM-свободой и детерминированным контролем

```
ОПЕРАТОР → задача (natural language)
    ↓
LLM PLANNER (genерирует TaskGraph)
    ↓
VALIDATION GATE (schema + skill-compliance + risk-class) ← ДЕТЕРМИНИРОВАНО
    ↓ accept          ↓ reject
5-gate loop       FAIL-CLOSED (эскалация оператору)
    ↓
VISION postcondition-check
    ↓ pass            ↓ fail
next node        RECOVERY LADDER (LLM с новым контекстом состояния)
                     ↓
                 новый узел → VALIDATION GATE (повтор)
```

LLM никогда не обходит VALIDATION GATE — ни при первоначальной декомпозиции,
ни при реактивном переплане. Это структурный инвариант, не конфигурация.

## Открытый вопрос A1

**Где ровно проходит граница «pre-frozen» vs «reactive»?**

Варианты:
- **Full-upfront:** LLM генерирует всё дерево перед первым шагом → оператор одобряет
- **Lazy-unfolding:** LLM генерирует по одному узлу перед каждым шагом (реактивно по postcondition)
- **Hybrid (рекомендуется):** LLM генерирует верхний уровень (1-2 слоя) для review оператором, затем
  реактивно раскрывает листовые узлы в допустимых границах предодобренного контракта

Рекомендация: **hybrid-lazy** — оператор pre-approves план/контракт + risk-boundaries,
а реактивное раскрытие свободно внутри этих валидированных границ.
Это решает latency-vs-safety трейдоф: не нужен per-step confirm там, где риск уже одобрен.
