# PROJECT BRIEF — Слой-ПЛАНИРОВЩИК для ЛАПЫ

_Decision: dec-20260622-034947-faca07 | Phase 0 — Discuss-First | Status: ожидает ревью оператора_

---

## Контекст: что такое ЛАПА сейчас

ЛАПА — детерминированные «руки» оператора на Windows. Архитектурная спина:
один 5-гейтовый loop (`PERCEIVE → RESOLVE → PROVE → ACT → VERIFY`), строгие гарантии:
- fail-closed на любом гейте (типизированная ошибка, не fallback)
- STOP: глобальный хоткей + файл-флаг, проверяется между каждым гейтом
- Declared-risk ladder: риск декларирует **вызывающий** в контракте, ЛАПА не угадывает
- Vision: perception-only, lazy (только при промахе UIA), возвращает selector-refinement, никогда не кликает по координатам

Доступные навыки сейчас: `open-app`, `type`, `telegram-send`, `telegram-send-sticker`.

Все они реализуют **заданную, конкретную последовательность** действий.
ЛАПА надёжно выполняет то, что ей сказали делать. Но **не умеет планировать сама**.

---

## Главный пробел

**Планирование — на операторе.**

Оператор (Claude / пользователь) раскладывает задачу «отправить сообщение» или
«найди и открой файл в Telegram» в конкретные шаги: какое окно, какое поле, что напечатать.
ЛАПА получает уже готовую атомарную инструкцию.

Это работает для простых навыков. Но не масштабируется на высокоуровневые задачи вида:
- «Зайди в Telegram, найди чат с Иваном, прочитай последнее сообщение и ответь по контексту»
- «Открой настройки системы, найди тёмную тему и включи»
- «Зайди в браузер, открой страницу X, заполни форму по данным из файла»

Для таких задач оператор должен вручную написать декомпозицию в шаги. Это медленно,
не масштабируется, и не позволяет ЛАПЕ адаптироваться к неожиданным состояниям UI.

---

## Цель

Добавить слой-ПЛАНИРОВЩИК поверх существующих надёжных рук:

> ЛАПА получает **высокоуровневую задачу** на естественном языке.
> ПЛАНИРОВЩИК (LLM) сам декомпозирует её в последовательность loop-действий.
> Каждое действие выполняется через существующий 5-гейтовый loop — **без обхода гарантий**.
> ЛАПА сама адаптируется к состоянию UI, использует Vision когда застряла,
> восстанавливается после провала шага или запрашивает оператора.

## Жёсткие ограничения (нельзя нарушать)

| # | Ограничение | Почему нельзя нарушать |
|---|-------------|----------------------|
| C1 | ПЛАНИРОВЩИК не исполняет действия напрямую | Единственная точка принуждения — 5-гейтовый loop |
| C2 | Закрытый словарь навыков: только `open/type/telegram/vision` | LLM не должен изобретать опасные действия |
| C3 | STOP остаётся глобальным и преемптивным | Оператор должен иметь возможность немедленно остановить всё |
| C4 | Declared-risk ladder сохраняется и re-проверяется на каждом шаге | Риск per-node, не только per-task |
| C5 | Vision остаётся perception-only, никогда не кликает | VISION-PROPOSES-UIA-DISPOSES — структурный инвариант |
| C6 | Никаких исполняемых атомов до одобрения оператора | Discuss-First, DA09 |

## Критерий успеха

Оператор может передать ЛАПЕ задачу вида `"Отправь в Telegram Ивану сообщение с текстом из файла X"`
и ЛАПА **сама**:
1. Декомпозирует задачу в шаги
2. Выполняет каждый шаг через 5-гейтовый loop
3. Проверяет результат каждого шага через Vision/UIA
4. Восстанавливается или эскалирует при провале
5. Запрашивает confirm для высокорисковых действий с конкретным payload
6. Останавливается по STOP немедленно
