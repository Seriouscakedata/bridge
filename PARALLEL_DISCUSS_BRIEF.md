# DISCUSS-ONLY — Guard-Driven Parallel (заказ оператора, 2026-06-03)

**Обсудите вместе. В ЭТОМ ходе ничего НЕ реализовывать — только спроектировать. Держите STATUS: DISCUSS пока не закончите проработку.**

## Проблема (корень — диагностировано)
Мост НЕ параллелит сам, хотя механизм есть. Причина: решение параллелить отдано МОДЕЛИ как опциональная возможность (планировщик должен сам эмитить `[[PARALLEL:N]]`), а модель не берёт опциональные возможности проактивно — **тот же паттерн, что с DecisionContract hint** (доказано: модель игнорит опциональный `[[DECISION]]`). Факты:
- `driver/86` диспетчит параллель ТОЛЬКО если в ответе уже ≥2 блока `[[PARALLEL:N]]`;
- детерминированного авто-анализа «эта задача распараллеливаема → разбей» для обычных задач НЕТ; есть только для backlog batch (`lib/backlog.ps1` сам строит `[[PARALLEL]` из независимых пунктов);
- `driver/30` сам жалуется: «планировщик эмитил `[[PARALLEL]` только на первом ходе — пропуск возможности»;
- self-model (Гл.1) показал: `multi-channel-parallel-drivers` (Start-ChannelDriver) в статусе **dormant**.

## Цель
Спроектировать **guard-driven parallel**: детерминированный механизм, чтобы мост САМ распараллеливал работу когда это **возможно и безопасно** — не завися от инициативы модели. По тому же принципу, что мы приняли: **модель ПРЕДЛАГАЕТ `parallel_groups`, deterministic guard ВАЛИДИРУЕТ безопасность и ПРИМЕНЯЕТ** (или откатывается на последовательное).

## Нужно
1. **Инвентаризация существующего:** `lib/parallel.ps1` (Invoke-ParallelWorkers/CodexParallel/worker-pool/complexity-floor), `driver/86` dispatch (≥2 `[[PARALLEL]` trigger), `lib/backlog.ps1` авто-`[[PARALLEL]` (рабочий прецедент детерминированного решения), DecisionContract `parallel_groups` (уже есть в shadow), `multi-channel-parallel-drivers`/Start-ChannelDriver (почему dormant?).
2. **Критерий безопасности параллели:** когда параллель БЕЗОПАСНА (touch-sets файлов НЕ пересекаются; нет shared mutable state; НЕ control-plane; нет порядковых зависимостей) и когда НЕТ (пересекающиеся файлы; control-plane: supervisor/watchdog/driver-loop; verify/critic-цепочки).
3. **Guard-дизайн:** model предлагает `parallel_groups` → guard детерминированно проверяет независимость (touch-sets, не control-plane) → диспетчит через `lib/parallel.ps1` в изолированных worktrees; конфликты/сомнение → fallback на последовательное.
4. **Разобрать `multi-channel-parallel-drivers` dormant:** сломан / не нужен / выключен? Чинить или формализовать как осознанно-выключенный.
5. **Shadow-first (как DecisionContract):** сначала ЛОГИРОВАТЬ «guard бы распараллелил так: groups=[...]» vs что реально произошло (sequential/parallel) — собрать evidence, и только потом включать реальный авто-dispatch. Не включать вслепую.
6. **План реализации АТОМАМИ** с тестами и acceptance criteria.

## Нельзя
- параллелить control-plane (supervisor.ps1/watchdog.ps1/driver loop/circuit-breaker);
- параллелить пересекающиеся touch-sets (гонки/конфликты записи);
- ломать critic/verify/QA-цепочки (их порядок важен);
- форсировать параллель там, где она вредна или рискованна;
- мутировать файлы параллельно без worktree-изоляции;
- включать авто-dispatch до накопления shadow-evidence.

## Ориентир архитектуры (от оператора — обсудите/улучшите)
- Переиспользовать `lib/parallel.ps1` + прецедент backlog-авто-`[[PARALLEL]` + DecisionContract `parallel_groups`. НЕ плодить новый параллель-движок.
- Тот же каркас, что Self-Model/Intent-Shadow: **shadow → evidence → guard-apply**, fallback на текущее последовательное поведение всегда сохранён.

## Результат обсуждения
