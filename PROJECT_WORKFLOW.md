# Project Delivery Workflow — инструкция для агента-оркестратора

> Это самодостаточная инструкция для ЛЮБОГО ИИ-агента (Claude, Codex, …), который ведёт разработку
> проекта **через мост** (bridge — автономная команда AI-воркеров). Прочитай целиком до начала работы.
> Операционные детали моста (команды, пульт, troubleshooting) — в `OPERATOR_GUIDE.md`.
>
> Версия флоу: 2026-06-01 (Discuss-First + декомпозиция до атомов).

---

## 0. ЖЕЛЕЗНОЕ ПРАВИЛО: новый проект = новая вкладка (новый канал)

Мост делит работу на **каналы**. Один канал = один проект = одна «вкладка» в пульте. Каналы лежат в
`bridge\channels\<slug>\` (свой state, бэклог, история на канал).

**Категорически:**
- **Новый проект → создай НОВЫЙ канал.** Никогда не веди новый проект в чужом канале (`aipartners`,
  `main`, `travel` уже заняты своими проектами). Иначе задачи и история двух проектов смешаются.
- **Один канал — один проект.** Не клади вторую идею/проект в существующую вкладку.
- **`main`** — это канал развития самого моста, НЕ для пользовательских проектов.

**Как создать новый проект (= канал):** через мост, функция `New-Project` (`lib/foundry.ps1`):
создаёт git-репозиторий проекта И привязывает к нему отдельный канал. Параметры: `Slug` (короткое имя
канала), `Name`, `Description`, `Goal`, `ParentDir`. Возвращает `{ ok, slug, projectRoot, channel }`.
После этого вся работа над проектом идёт В ЭТОМ канале (`?channel=<slug>` в пульте).
Проверка: `[[DISPATCH-DAG]]` и параллель не запустятся, пока канал не привязан к проекту — это
встроенная защита от «работы не в той вкладке».

> Первый шаг ВСЕГДА: убедись, что ты в правильном канале своего проекта. Сомневаешься — создай новый.

## 1. Роли (не смешивать)

| Роль | Кто | Делает | НЕ делает |
|---|---|---|---|
| **Оператор** | человек | даёт намерение; ревьюит ТОЛЬКО уровень глав; приёмка | не лезет в мелкую декомпозицию |
| **Ты (агент-оркестратор)** | Claude/Codex | формулируешь вход мосту, ревьюишь выход, ведёшь декомпозицию ниже глав, честно докладываешь | НЕ исследуешь/планируешь/кодишь в своём контексте — делегируешь мосту |
| **Мост-команда** | AI-воркеры | обсуждает, планирует, декомпозирует, пишет код, проверяет | — |

---

## 2. Принципы

1. **Не тяни мышление в свой контекст.** Исследование, обсуждение, карта, план, декомпозиция, код —
   делегируй мосту (режим DISCUSS). Ты = формулировка входа + ревью выхода. (Типовая ошибка: сам всё
   исследовал и накидал беклог кусками → получился франкенштейн: страницы есть, навигации/логики нет.)
2. **Не на скорую руку.** Сначала обсуждение → план → ревью → и только потом исполнение.
3. **В беклог идут только АТОМЫ** (см. §4). Крупный этап в беклоге = воркер на большой задаче ломает.

## 3. Discuss-First — фазы

| Фаза | Кто | Что |
|---|---|---|
| Ф0 Намерение | оператор | цель проекта одной формулировкой |
| Ф1 Обсуждение | **мост** (DISCUSS) | сам исследует проект, вскрывает нестыковки, задаёт вопросы. Запуск: задача с маркером `[[DEEP-THINK]]` на отдельной строке → Claude↔Codex обсуждают без правок кода |
| Ф2 Карта+план | **мост** | формирует `PROJECT_MAP.md` (текущее→целевое, маршруты, навигация, пути пользователя) + `PLAN.md` (этапы=главы, зависимости, критерии готовности, риски). Discuss не пишет файлы — нужна отдельная задача «запиши в .md» |
| Ф3 Ревью плана | ты | архитектор-гейт: целостность, дыры, риски → возврат мосту на итерацию |
| Ф4 Ревью глав | оператор | смотрит список ГЛАВ + продуктовые развилки, утверждает |
| Ф5 Заморозка | — | план зафиксирован → разрешён беклог |
| **Декомпозиция** | **мост + ты** | каждую главу дробишь до атомов (§4) |
| Ф6 Исполнение | **мост-команда** | беклог атомов; verify ОБЯЗАН гонять project build/tsc, не только smoke; задача не закрывается пока не собирается |
| Ф7 Приёмка | оператор | проверка «флоу как в карте», сквозные сценарии — не «зелёный build» |

## 4. Декомпозиция до АТОМОВ (книга → главы → … → атомы)

Крупная задача дробится как книга:

| Уровень | Что | Пример | Кто ревьюит |
|---|---|---|---|
| 📕 Книга | проект целиком | «связный продукт X» | оператор |
| 📑 Глава | крупный этап, законченная ценность | «Навигация», «Auth» | **оператор (только этот уровень!)** |
| 📃 Параграф | подсистема главы | Header / Footer / layout | ты |
| ¶ Абзац | конкретный аспект | «Header: меню гостя» | ты |
| · **Атом** | 1 файл / 1 маленькое проверяемое изменение | «добавить в Header ссылку Войти» | ты |

**Правила декомпозиции:**
- **В беклог — ТОЛЬКО атомы.** Глава/параграф/абзац — структура обсуждения, не задачи беклога.
- **Критерий атома:** 1 файл (или 1 маленький компонент) + одно проверяемое изменение + само
  проходит `tsc`/build. Если трогает >1–2 файла или содержит «и ещё» — дробить дальше.
- **Поглавно:** декомпозируй ОДНУ главу → атомы → ревью → беклог → исполнение → следующая глава.
  Не вываливай 100+ атомов разом.
- **Глубина по размеру:** мелкая глава → сразу в атомы (2 уровня); крупная → через параграфы/абзацы.
- **Декомпозицию ведёт мост** (на сложных местах — DISCUSS), ты ревьюишь что атомы реально атомарны.

---

## 5. Разграничение ревью (жёстко)

- **Оператор ревьюит ТОЛЬКО главы** (список крупных этапов + продуктовые развилки).
- **Всё мельче глав — на тебе** (параграфы, абзацы, атомы; целостность и атомарность).
- Не таскай оператора в мелкую декомпозицию. К нему возвращайся с результатом ГЛАВЫ, не с атомами.

---

## 6. Технически — как прогнать главу через мост

1. **Канал.** Убедись, что ты в канале своего проекта (§0). Новый проект → `New-Project`.
2. **Запустить обсуждение/декомпозицию (DISCUSS):** добавь в бэклог канала задачу с `[[DEEP-THINK]]`
   на отдельной строке + темой. Мост обсудит без правок.
3. **Зафиксировать результат (карта/план/атомы):** отдельной задачей `[[NORMAL]]` попроси мост
   ЗАПИСАТЬ согласованное в durable-файлы (MAP/PLAN) или сформировать список атомов.
4. **Добавлять задачи в бэклог — под паузой** (driver перезаписывает бэклог; прямой append во время
   работы затирается):
   - поставить `state.paused=true` → подождать → дописать атомы в `backlog.jsonl` (UTF-8 БЕЗ BOM,
     `status:'approved'`, у каждого свой `workpack_conflict_group='file:<путь>'` и
     `workpack_touch_set` — тогда независимые атомы пойдут параллельно) → `state.paused=false`.
   - детали и точные команды — `OPERATOR_GUIDE.md` §3.
5. **Исполнение:** мост сам берёт approved-атомы, параллелит независимые (packer → worktree-воркеры
   → collect-then-commit). Verify гоняет `tsc`/build.
6. **Наблюдение:** не вмешивайся в реализацию; следи за чатом канала и git-коммитами; честно
   докладывай оператору результат ГЛАВЫ.

## 7. Гейты и чеклист (перед тем как двигаться дальше)

- [ ] Работаю в правильном канале (новый проект → новый канал)?
- [ ] Был ли DISCUSS перед беклогом (а не «накидал кусками»)?
- [ ] Есть утверждённый оператором список глав?
- [ ] В беклоге — атомы, а не главы?
- [ ] Verify гоняет project build/tsc (не только smoke)?
- [ ] Приёмка против карты (сквозной сценарий), а не «build зелёный»?

---

## 8. Анти-паттерны (чего НЕ делать)

- ❌ Вести новый проект в существующем чужом канале (смешение проектов).
- ❌ Самому исследовать/планировать/кодить в своём контексте вместо делегирования мосту.
- ❌ Кидать в беклог крупные этапы («главы») вместо атомов.
- ❌ Грузить беклог без обсуждения и утверждённого плана.
- ❌ Закрывать задачу по «зелёному build», не проверив сценарий продукта.
- ❌ Хвалиться результатом, не проверив реально (страницы есть ≠ продукт работает).

---

*Этот флоу проверяется на практике. Если шаг неудобен или мост чего-то не умеет (например, DISCUSS
не пишет файлы — нужна отдельная задача на запись) — фиксируй как доработку моста, не обходи флоу.*
